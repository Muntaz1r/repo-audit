Problem Statement

Reviewing a repo by hand doesn't scale.

/* why this project exists */

Engineers evaluate unfamiliar GitHub repositories every day — before adopting a library, reviewing a contribution, or auditing an internal service. Today that evaluation is manual, slow, and inconsistent: someone skims the README, greps for obvious red flags, and forms a judgment on gut feel.

There is no single tool that takes a public GitHub repository URL and returns a structured, evidence-backed report covering what the codebase does, how well it's built, how secure it is, how well it's documented, and whether it's actually ready for production use.

The intern's task is to design and build exactly that platform: paste a repo link in, get a structured review out.

The Mission

Build a platform that reviews any public repo, automatically.

A user submits a GitHub URL. The platform fetches the repository and runs it through five analysis pillars, then presents the findings as a clear, navigable report — no manual digging required.

  • 01
    Accept a public GitHub URLValidate the link, resolve the default branch, and fetch repo metadata via the GitHub API.
  • 02
    Pull the sourceClone or fetch the repository contents into an isolated analysis environment.
  • 03
    Run the five-pillar reviewSemantic analysis, code evaluation, security, documentation, and production-readiness — each producing findings and a score.
  • 04
    Present a structured reportOne dashboard per repo: overall verdict, category scores, and specific, actionable findings.
What Gets Reviewed

Five pillars, one verdict.

PILLAR 01

Semantic Analysis

What does this code actually do? Infer purpose, architecture, module boundaries, and key dependencies between components.

PILLAR 02

Code Evaluation

Quality, complexity, duplication, code smells, test coverage, and adherence to language-idiomatic conventions.

PILLAR 03

Security

Known-vulnerable dependencies, hardcoded secrets, unsafe patterns, and exposed attack surface.

PILLAR 04

Documentation

README quality, setup instructions, inline comments, and coverage of public APIs and interfaces.

PILLAR 05

Production Readiness

CI/CD presence, error handling, logging, licensing, and overall shippability of the codebase.

How It Works

From URL to verdict.

01

Submit

User pastes a public GitHub repo URL into the platform.

02

Fetch

Repo is cloned and metadata is pulled from the GitHub API.

03

Analyze

Static tools + AI-assisted analysis run across all five pillars.

04

Score

Each pillar produces findings and a normalized score.

05

Report

Results render as a structured, shareable dashboard.

Deliverables & Success Criteria

What "done" looks like.

Deliverables

  • A working web app with a single input field for a GitHub URL
  • A backend pipeline that fetches and analyzes any public repo
  • A report UI showing all five pillars with scores and findings
  • An overall production-readiness verdict per repo
  • Exportable / shareable report output

Success Criteria

  • Works on any valid public GitHub repository URL
  • Returns a complete report within a reasonable time budget
  • Findings are specific — not generic pass/fail labels
  • Handles large, small, and malformed repos gracefully
  • Report is understandable to a non-author reviewer
Suggested Tech Stack

Starting points, not requirements.

Build and test locally first, then mirror the same pieces onto AWS for a deployed, always-on version.

BACKENDNode.js or Python (FastAPI)

SECURITY SCANNINGTrivy, npm audit, Bandit, Semgrep
SEMANTIC ANALYSISLLM-based code understanding (Claude API)
DOCS SCORINGHeuristic README / docstring coverage checks
STORAGEPostgreSQL for reports + repo metadata

Local vs. AWS Deployment

LOCAL DEVDocker Compose — app, DB & analyzers on one machine
AWS COMPUTEECS / Fargate (or EC2) to run the app + analysis workers
AWS REPO ANALYSIS JOBSAWS Lambda / Batch for on-demand clone-and-scan tasks
AWS STORAGERDS (PostgreSQL) for reports + S3 for cloned repo artifacts
AWS SECRETSSecrets Manager for GitHub tokens & API keys
AWS DELIVERYAPI Gateway + CloudFront for the frontend/API endpoints
Next Step

Pick a repo. Start with one pillar.

Don't try to build all five pillars at once. Start with a working end-to-end path for one pillar — code evaluation is usually the easiest first slice — then widen. A thin, working pipeline beats five half-built analyzers.

- manual, ad-hoc repo review
+ repo-audit review <url> → structured verdict
